# Milestone 14 — internal API, MCP server, embedded agent

Introduces the agent surface of Halemans: an internal (unstable) JSON API, a
standalone MCP stdio server, and the embedded agent behind a floating chat
widget on every page. Also adds the `not-in` match operator for dashboard
cards. Decisions from the design discussion:

- ONE tool implementation (`Application/Service/Agent/Tools.hs`) backs all
  three surfaces. Executors are request-independent — they take an explicit
  act-as `AgentContext` (user + display language) instead of
  `?request`/`currentUser` — so the same code runs in the web process, the
  worker and the stdio MCP server.
- The internal surface is deliberately text-shaped (`{"result": <text>}`):
  it is unstable by charter, so no schema commitments are made here. When an
  endpoint proves stable and useful it graduates to `/api/v1` with a real
  JSON schema (this is also the MCP tools' path to becoming public).
- MCP over stdio (protocol 2025-03-26): the local agent is a separate
  process in the same trust domain, so transport auth is the environment,
  not tokens on the wire. The server acts as a DEDICATED SERVICE ACCOUNT —
  user `mcp@localhost` (unusable `"!"` password hash) bound to a dedicated
  `mcp` role — auto-created idempotently at first boot. The role starts
  with the minimal `["view"]` privilege; widening it is an administrator
  decision. `HALEMANS_MCP_USER` switches to another existing user;
  `HALEMANS_MCP_PRIVILEGES` (comma-separated, validated against
  `allPrivileges`) pins the role's privileges from env — when set it is
  re-synced on every boot and overrides UI edits; when unset the role is
  created with `["view"]` if missing and otherwise left alone.
- Mutating tools use a two-phase confirm flow (`confirmed` argument), not
  session state: `confirmed=false` returns the validation plan, the model
  shows it to the user, `confirmed=true` applies. Simple, auditable,
  resumable.

## 1. Tool registry (`Application/Service/Agent/Tools.hs`)

M1 tools, all soft-failing with in-band text (same convention as
`Application.Service.Llm.Tools`):

| Tool | Kind | Notes |
|---|---|---|
| `list_environments` | read | envs + open-alert counts; requires `view` privilege of the act-as user |
| `list_dashboards` | read | the act-as user's dashboards |
| `get_dashboard_schema` | read | static card-config doc (facet refs, ops, example) |
| `validate_dashboard` | dry-run | decodes card JSON, counts matching open alerts per card via `cardBaseQuery`/`fetchCount`, returns a plan |
| `create_dashboard` | mutate | two-phase `confirmed` flow; per-user resource, no extra privilege |
| `search_alerts` | read | reuses the public `listAlertsPage` filters |
| `get_llm_config` | read | provider name/model/endpoint only, never the API key |

Tool JSON follows the OpenAI function shape so the same definitions feed
both the LLM tool loop (`agentToolDefinitions`) and MCP `tools/list`.

## 2. Internal HTTP API (`Web/Controller/InternalApi.hs`)

Routes under `/api/internal/*` (`Web/Routes.hs`); each action wraps the tool
executor and returns `{"result": <text>}`. Auth in
`Application/Service/Api/InternalAuth.hs`:

- Disabled entirely unless env `HALEMANS_INTERNAL_TOKEN` is set (503).
- Requires marker header `X-Halemans-Internal: 1` (404 without — accidental
  external reliance stays visible), `Authorization: Bearer <token>` (401),
  and `X-Act-As: <email>` resolving to an existing user (403).
- Granted calls insert a row into `internal_api_audit` (user, method, path).
  The audit lives in the DB because the web layer has no `FastLogger`
  (`Application.Service.Log` is job-context only) — and a queryable trail
  beats log lines anyway.
- Per-act-as-user rate limit, same in-memory token bucket as the public API.

## 3. MCP server (`Application/Service/Agent/Mcp.hs`, `exe:HalemansMcp`)

Newline-delimited JSON-RPC over stdio (`initialize`, `ping`, `tools/list`,
`tools/call`; notifications are acked silently). The exe is a
`runScript`-style entry (`Application/Script/HalemansMcp.hs`) generated by
`docker/prepare-cabal-build.sh` like the other script wrappers.
`tools/call` results carry `isError` for the `unknown tool` / `invalid
arguments` / `forbidden` prefixes.

Act-as identity is `resolveMcpUser`: `HALEMANS_MCP_USER` names an existing
user; otherwise the default service account (`mcp@localhost` + `mcp` role)
is auto-created (see the milestone header decisions for the privilege
sync rules).

## 4. Embedded agent (`Web/Controller/AgentChat.hs` + `Application/Service/Agent/Core.hs`)

- Floating widget in `Web/View/Layout.hs` (logged-in only; all behavior in
  `static/app.js` per the CSP policy; brand-layer CSS). The client sends
  `{message, session_id, page_context}`; `page_context` (`path`, `title`)
  is gathered on send and stored on the session + first message, then
  injected into the system prompt. The input row is deliberately NOT a
  `<form>`: IHP's `helpers.js` XHR-submits every form on the site
  (`initDisableButtonsOnSubmit`), so JS-driven forms are `div` + plain
  button + Enter `keydown`, with events delegated at document level
  (turbolinks-morphdom patches can drop per-node listeners).
- `POST /agent/chat` creates or resumes an owned session, persists the user
  message, runs the turn, returns the persisted assistant rows.
  `GET /agent/sessions` / `GET /agent/chat/:id` back the resume dropdown and
  history render.
- `Core.runAgentTurn` rebuilds the OpenAI message list from
  `agent_messages`: assistant rows with `tool_calls` JSON regenerate the
  assistant message plus one tool-result message per call, with
  deterministic ids `m<rowIndex>-<callIndex>` — so tool/result pairing
  survives the DB round trip without storing raw provider payloads.
- Provider resolution reuses `currentLlmConfig` (DB-first, the admin/llm
  page; env fallback). Daily-token budget (`llm_budget_counters`) is checked
  and incremented per completion; `maxToolRounds = 6`.
- The system prompt pins: act-as identity, response language (from
  `users.settings.language`), tool grounding ("never invent ids or
  counts"), the strict two-phase flow for mutating tools, and the match-op
  vocabulary.

## 5. Schema (migrations `1790154689-agent-chat.sql`, `1790179252-agent-budget.sql`)

- `agent_sessions` — id, user_id→users, title, page_context jsonb, timestamps.
- `agent_messages` — id, session_id→agent_sessions ON DELETE CASCADE,
  role (`user`|`assistant`), content, tool_calls jsonb
  (`[{name, arguments, result}]`), tool_call_id, page_context, prompt/completion
  token counts, created_at.
- `internal_api_audit` — id, user_id→users, method, path, created_at.
- `llm_agent_configs` — singleton (no row = 200k tokens/day, 12 req/min):
  the agent chat's DEDICATED budget, editable on the admin/LLM page
  (Agent chat card). The analysis pipeline keeps its own env-based budget
  (`LLM_DAILY_TOKEN_BUDGET`) — the two no longer race on one shared cap.
- `llm_budget_counters.scope` — `'analysis'` (default, backfilled) vs
  `'agent'`; unique (scope, provider, day).

## 6. `not-in` match operator

`MatchOp` gains `OpNotIn` (JSON op string `"not-in"`, `values` array like
`in`): parser + re-encoder (`Application/Helper/DashboardConfig.hs`),
Haskell matcher (`notElem`, Nothing never matches), and SQL
(`NOT IN`, with the existing `IS NOT NULL` guard keeping NULL-semantics
identical to the Haskell side) in `Application/Service/DashboardCards.hs`.
Nothing else pattern-matches on `MatchOp`, so the vocabulary change is
contained; provision files accept it transparently since they decode through
the same `decodeDashboardConfig`.

## 7. Admin/LLM additions

- The Effective configuration card gains a **Test integration** button next
  to the Test connection (GET /v1/models). `Llm.testIntegration` sends
  "Reply with exactly one word: pong" in non-streaming mode (empty content
  counts as success when the provider still generated tokens — reasoning
  models starve a small max_tokens), then with `stream: true`, verifying the
  buffered SSE body has `data:` chunks and a `[DONE]` terminator
  (15s per-phase timeout; errors name the mode). mock-llm honors `stream`.
- **Agent configuration page** (`/admin/llm/agent`, Admin → Agent):
  - *Agent prompt*: the ACTIVE `internal_agent` row of
    `llm_prompt_templates` — the chat agent's system prompt, versioned and
    edited in the same template editor as `alert_enrichment`. Slots:
    `{{user_name}}`, `{{user_email}}`, `{{language}}`,
    `{{current_page_url}}`, `{{current_page_title}}` (the URL carries
    path + query — the `/alerts` view state lives in the query string).
    Seeded at v2 by `seed-halemans.sh`/`smoke-check.sh`; "Create template
    from default" seeds it from `Core.defaultAgentTemplateBody`. Without an
    active row the agent uses the identical built-in default. The legacy
    `{{page_context}}` JSON slot keeps working for v1 rows.
  - *Agent limits*: the per-agent daily token budget + requests/min
    (`llm_agent_configs`).
  - *Global limits*: `llm_global_configs` singleton caps ALL LLM consumers
    (analysis + agent) with `LLM_DAILY_TOKEN_BUDGET`/`LLM_RATE_PER_MINUTE`
    as env fallbacks; the analysis pipeline's budget check and rate limit
    consume this. Enforcement: per-consumer cap first, then the global one
    (`Core.agentTurnGate`), so a runaway consumer can't starve the others.

## 8. Tool registry (P1–P3, RBAC-gated)

The registry covers the Halemans subsystems in three phases (43 tools):

- **P1 day-2 ops**: alert actions (ack/unack/close/comment), blackouts
  (list/create/delete), dashboards (create/validate/update/delete/set
  default/schema).
- **P2 configuration**: teams + members, escalation policies (steps as
  JSON), notification rules, grouping rules, sources (list/enable/disable).
- **P3 user + admin reads**: profile get/update, own API tokens
  (create returns the plaintext once), users/roles, LLM templates/providers,
  alert groups.

**RBAC is enforced server-side, never by the model** (design rule): every
catalog entry carries its required privilege; `executeAgentTool` checks the
act-as user's real privileges (`userPrivileges`, `admin` implies all) BEFORE
dispatch and hard-fails with "forbidden: …"; `agentToolDefinitionsFor` filters
the tool list sent to the LLM (and MCP `tools/list`) so the model never sees
tools it cannot call. Provisioned-protected config rows refuse mutations, and
mutating tools keep the two-phase `confirmed` flow. E2E-verified against a
real Qwen3 (llama.cpp): plan → user confirms → blackout applied → DB row.

## 9. Tests

- `Test/DashboardConfigSpec.hs` — not-in matcher, JSON round-trip, empty
  `values` rejection.
- `Test/AgentSpec.hs` (unit) — tool-definition shape: names, required
  params, `confirmed` optional.
- `Test/LlmSpec.hs` (unit) — `verifyStreamBody` SSE shape checks.
- `Test/Integration/LlmSpec.hs` — `testIntegration` against the mock
  (non-streaming + streaming ping).
- `Test/Integration/AgentSpec.hs` — executor against a scratch PG (env
  listing, validate counts, two-phase create, privilege-gated search,
  soft-fails), the MCP protocol (initialize/tools list/tools call
  isError/notification silence/unknown-method error), the default service
  account (idempotent auto-create, single dedicated role,
  `HALEMANS_MCP_PRIVILEGES` sync, explicit-user resolution), the turn loop
  (tool rounds regression + exhaustion rescue), template-based system
  prompt (fallback, bindings, slot coverage), the budget gate (agent cap /
  global cap / provider isolation) and the global config round-trip. The
  internal HTTP layer is a thin wrapper over the same executor; HTTP-level
  auth/audit checks are manual until a header-capable HTTP test harness
  exists.
